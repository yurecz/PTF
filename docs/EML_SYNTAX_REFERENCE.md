# EML (Entity Manipulation Language) Syntax Reference

## Overview

This document consolidates EML syntax knowledge for PTF development, specifically focusing on `MODIFY ENTITIES ... OPERATIONS` dynamic form used by PTF's MODIFY action.

**Official ABAP Documentation:**
- Base URL: `https://ldciemo.wdf.sap.corp:44300/sap/public/bc/abap/docu`
- Key Object IDs:
  - `ABENEML` - EML overview
  - `abapmodify_entity_entities` - MODIFY statement
  - `abapmodify_entities_operations_dyn` - Dynamic operations variant (PTF uses this)
  - `abapeml_response` - Response parameters (FAILED/REPORTED/MAPPED)

## MODIFY ENTITIES OPERATIONS Statement

PTF uses the dynamic operations variant:

```abap
MODIFY ENTITIES OF root_entity
  OPERATIONS operation_tab
  FAILED DATA(ls_failed)
  REPORTED DATA(ls_reported)
  MAPPED DATA(ls_mapped).
```

**Operation Table Type:** `ABP_BEHV_CHANGES_TAB`

**Structure Fields:**
- `op` (TYPE char01): Operation type constant from `if_abap_behv=>op-m-*`
- `entity_name` (TYPE abp_entity_name): Target entity name
- `sub_name` (TYPE abp_assoc_name): Association name (CREATE_BY) or action name (EXECUTE)
- `instances` (TYPE REF TO data): Table of operation-specific instances

## Operation Types

| Operation | Constant | Value | Purpose | %CID | %CID_REF |
|-----------|----------|-------|---------|------|----------|
| CREATE | if_abap_behv=>op-m-create | 'C' | Create new entity | ✅ | ❌ |
| CREATE_BY | if_abap_behv=>op-m-create_ba | 'O' | Create via association | ✅ (child) | ✅ (operation-level) |
| UPDATE | if_abap_behv=>op-m-update | 'U' | Update existing entity | ❌ | ✅ (instance-level) |
| DELETE | if_abap_behv=>op-m-delete | 'D' | Delete entity | ❌ | ❌ |
| EXECUTE | if_abap_behv=>op-m-action | 'A' | Execute action | ❌ | ✅ (instance-level) |

**MCP Verified:** All constants verified from IF_ABAP_BEHV interface (ERX/815, 2025-01-17)

## %CID and %CID_REF

### %CID (Content ID)

**Purpose:** Temporary identifier for newly created entities within a request, allowing other operations in the same request to reference them.

**Constant:** `cl_abap_behv=>co_techfield_name-cid` (value: '%CID')

**MCP Verified:** Constant verified from CL_ABAP_BEHV class line 19 (ERX/815, 2025-01-17)

**Supported Operations:**
- CREATE: Instance-level, auto-generated if omitted
- CREATE_BY: Instance-level (child entities), auto-generated if omitted

**Auto-Generation:** PTF automatically generates `%CID` if not provided in JSON (format: `cid_1`, `cid_2`, etc.)

**Example Usage:**
```abap
" CREATE with %CID
MODIFY ENTITIES OF i_salesordertp
  ENTITY salesorder
  CREATE FIELDS ( customername )
  WITH VALUE #( ( %cid = 'order-1' customername = 'ACME Corp' ) )
  MAPPED DATA(ls_mapped)
  FAILED DATA(ls_failed)
  REPORTED DATA(ls_reported).
```

### %CID_REF (Content ID Reference)

**Purpose:** References an entity created earlier in the same request using its %CID, without needing actual key values.

**Constant:** `cl_abap_behv=>co_techfield_name-cid_ref` (value: '%CID_REF')

**MCP Verified:** Constant verified from CL_ABAP_BEHV class line 20 (ERX/815, 2025-01-17)

**Supported Operations:**
- CREATE_BY: **Operation-level** placement
- UPDATE: **Instance-level** placement
- EXECUTE: **Instance-level** placement

**Not Supported:**
- DELETE: Keys required (no content ID support)

### Placement Rules Summary

| Operation | %CID Support | %CID_REF Support | %CID_REF Placement |
|-----------|--------------|------------------|-------------------|
| CREATE | ✅ Instance | ❌ No | N/A |
| CREATE_BY | ✅ Instance (child) | ✅ Yes | **Operation-level** |
| UPDATE | ❌ No | ✅ Yes | **Instance-level** |
| DELETE | ❌ No | ❌ No | N/A |
| EXECUTE | ❌ No | ✅ Yes | **Instance-level** |

## Operation-Specific Syntax

### CREATE Operation

**ABAP Structure:**
```abap
MODIFY ENTITIES OF i_salesordertp
  ENTITY salesorder
  CREATE FIELDS ( customername orderdate )
  WITH VALUE #( 
    ( %cid = 'order-1'
      customername = 'ACME Corp'
      orderdate = '20260117' )
  ).
```

**PTF JSON Format:**
```json
{
  "op": "CREATE",
  "entity": "SalesOrder",
  "instances": [
    {
      "%CID": "order-1",
      "CustomerName": "ACME Corp",
      "OrderDate": "2026-01-17"
    }
  ]
}
```

**Key Points:**
- %CID optional, auto-generated if omitted
- All non-key fields are settable
- Key fields typically auto-generated by BO

### CREATE_BY Operation

**ABAP Structure (Two-Level):**
```abap
MODIFY ENTITIES OF i_salesordertp
  ENTITY salesorder
  CREATE BY \_item
  FIELDS ( productid quantity )
  WITH VALUE #(
    ( %cid_ref = 'order-1'
      %target = VALUE #(
        ( %cid = 'item-1' productid = 'P100' quantity = 5 )
        ( %cid = 'item-2' productid = 'P200' quantity = 3 )
      )
    )
  ).
```

**PTF JSON Format (Simplified Single-Level):**
```json
{
  "op": "CREATE_BY",
  "entity": "SalesOrder",
  "sub_name": "_Item",
  "%CID_REF": "order-1",
  "instances": [
    {
      "%CID": "item-1",
      "ProductID": "P100",
      "Quantity": 5
    },
    {
      "%CID": "item-2",
      "ProductID": "P200",
      "Quantity": 3
    }
  ]
}
```

**Key Points:**
- %CID_REF at **operation level** (outside instances array)
- PTF deserializer creates proper two-level ABAP structure internally
- Parent key fields omitted when using %CID_REF
- Child %CID auto-generated if omitted
- Composite keys: Parent key part identifies association, child key part may be auto-generated

### UPDATE Operation

**ABAP Structure:**
```abap
MODIFY ENTITIES OF i_salesordertp
  ENTITY salesorder
  UPDATE FIELDS ( customername )
  WITH VALUE #(
    ( %cid_ref = 'order-1'
      customername = 'New Name' )
  ).
```

**PTF JSON Format:**
```json
{
  "op": "UPDATE",
  "entity": "SalesOrder",
  "instances": [
    {
      "%CID_REF": "order-1",
      "CustomerName": "New Name"
    }
  ]
}
```

**Alternative (Key-Based):**
```json
{
  "op": "UPDATE",
  "entity": "SalesOrder",
  "instances": [
    {
      "SalesOrder": "12345",
      "CustomerName": "New Name"
    }
  ]
}
```

**Key Points:**
- %CID_REF at **instance level** (inside each instance)
- Either %CID_REF OR key fields required (not both)
- Only changed fields need to be specified
- Use %CID_REF to update entities created in same request

### DELETE Operation

**ABAP Structure:**
```abap
MODIFY ENTITIES OF i_salesordertp
  ENTITY salesorder
  DELETE FROM VALUE #(
    ( salesorder = '12345' )
    ( salesorder = '12346' )
  ).
```

**PTF JSON Format:**
```json
{
  "op": "DELETE",
  "entity": "SalesOrder",
  "instances": [
    {"SalesOrder": "12345"},
    {"SalesOrder": "12346"}
  ]
}
```

**Key Points:**
- Key fields **required** (no %CID_REF support)
- Minimal payload: keys only
- Cannot delete entities by content ID
- Composite keys: All key parts required

### EXECUTE Operation (Actions)

**ABAP Structure:**
```abap
" Instance action
MODIFY ENTITIES OF i_salesordertp
  ENTITY salesorder
  EXECUTE approve
  FROM VALUE #(
    ( salesorder = '12345' )
  )
  RESULT DATA(lt_result).

" Static action (no key)
MODIFY ENTITIES OF i_salesordertp
  ENTITY salesorder
  EXECUTE recalculate
  FROM VALUE #( ( ) )
  RESULT DATA(lt_result).
```

**PTF JSON Format (Instance Action with Key):**
```json
{
  "op": "EXECUTE",
  "entity": "SalesOrder",
  "sub_name": "Approve",
  "instances": [
    {"SalesOrder": "12345"}
  ]
}
```

**PTF JSON Format (Instance Action with %CID_REF):**
```json
{
  "op": "EXECUTE",
  "entity": "SalesOrder",
  "sub_name": "Approve",
  "instances": [
    {"%CID_REF": "order-1"}
  ]
}
```

**PTF JSON Format (Static Action):**
```json
{
  "op": "EXECUTE",
  "entity": "SalesOrder",
  "sub_name": "Recalculate",
  "instances": [{}]
}
```

**Key Points:**
- `sub_name` contains action name from BDEF
- Instance actions: Require key fields OR %CID_REF
- Static actions: Empty instance `[{}]`
- %CID_REF at **instance level** (inside each instance)
- Action parameters passed as additional fields in instances
- Use %CID_REF to execute action on entity created in same request

**MCP Verified:** Action metadata available via `cl_abap_behv_load=>tt_action` table type with structure:
- `owner_entity` (TYPE abp_entity_name) - Entity owning the action
- `name` (TYPE abp_action_name) - Internal action name
- `ext_name` (TYPE rbdef_action-ext_name) - External CDS name

## Combining Operations in Single Request

Operations are executed in the order specified in the operations array:

```json
[
  {
    "op": "CREATE",
    "entity": "SalesOrder",
    "instances": [
      {
        "%CID": "order-1",
        "CustomerName": "ACME Corp"
      }
    ]
  },
  {
    "op": "CREATE_BY",
    "entity": "SalesOrder",
    "sub_name": "_Item",
    "%CID_REF": "order-1",
    "instances": [
      {
        "%CID": "item-1",
        "ProductID": "P100"
      }
    ]
  },
  {
    "op": "UPDATE",
    "entity": "SalesOrder",
    "instances": [
      {
        "%CID_REF": "order-1",
        "Status": "Confirmed"
      }
    ]
  },
  {
    "op": "EXECUTE",
    "entity": "SalesOrder",
    "sub_name": "Approve",
    "instances": [
      {"%CID_REF": "order-1"}
    ]
  }
]
```

**Workflow:**
1. CREATE SalesOrder with %CID 'order-1'
2. CREATE_BY creates Item under 'order-1' (using %CID_REF)
3. UPDATE the SalesOrder 'order-1' (using %CID_REF)
4. EXECUTE Approve action on 'order-1' (using %CID_REF)

**All operations execute in transactional buffer, committed together at end.**

## Response Parameters

### FAILED Response

Contains entities where operations failed with error severity.

**Structure:** `TYPE RESPONSE FOR FAILED <root_entity>`

**Example:**
```abap
IF ls_failed-salesorder IS NOT INITIAL.
  " Handle failed sales orders
  LOOP AT ls_failed-salesorder INTO DATA(ls_fail).
    " ls_fail-%cid or ls_fail-<key_field>
  ENDLOOP.
ENDIF.
```

### REPORTED Response

Contains messages reported during operation execution.

**Structure:** `TYPE RESPONSE FOR REPORTED <root_entity>`

**Message Severities:**
- Error (E) - Operation failed
- Warning (W) - Operation succeeded with warning
- Information (I) - Informational message
- Success (S) - Success message

### MAPPED Response

Contains key mappings for created entities (%CID → actual keys).

**Structure:** `TYPE RESPONSE FOR MAPPED <root_entity>`

**Example:**
```abap
LOOP AT ls_mapped-salesorder INTO DATA(ls_map).
  " ls_map-%cid = 'order-1'
  " ls_map-salesorder = '12345' (actual generated key)
ENDLOOP.
```

## PTF Integration

### cl_ptf_rap_modify_json Class

**Purpose:** Deserializes PTF JSON to ABP_BEHV_CHANGES_TAB structure

**Key Method:** `deserialize_to_operations_table()`

**Input:** JSON string with operations array
**Output:** Typed operation table for `MODIFY ENTITIES ... OPERATIONS`

**Special Handling:**
- CREATE_BY: Converts single-level JSON to two-level ABAP structure with %target
- %CID auto-generation: Generates unique IDs when not provided
- %CID_REF extraction: Operation-level for CREATE_BY, instance-level for UPDATE/EXECUTE
- Field name mapping: Internal ABAP names → External CDS names (via DD03ND)

### cl_ptf_rap_modify_template Class

**Purpose:** Generates example JSON templates for each operation type

**Key Method:** `generate()`

**Input:** Entity name
**Output:** JSON template with all available operations

**Template Generation:**
- Fetches entity metadata (key fields, associations, actions)
- Generates CREATE with all non-key fields
- Generates CREATE_BY for each association
- Generates UPDATE with all modifiable fields
- Generates DELETE with key fields only
- Generates EXECUTE for each action (instance and static)

**MCP Verified:** Uses verified APIs:
- `cl_abap_behvdescr=>create_data()` - Factory for typed structures
- `cl_abap_behv_load=>tt_action` - Action metadata table

## Best Practices

### When to Use %CID

- Assign %CID to entities that will be referenced by other operations
- CREATE operations that have child entities via CREATE_BY
- UPDATE/EXECUTE operations may reference created entities

### When to Use %CID_REF

- CREATE_BY referencing newly created parent
- UPDATE modifying entity just created
- EXECUTE running action on newly created entity

### Operation Order

1. CREATE parent entities first
2. CREATE_BY child entities (referencing parents)
3. UPDATE entities as needed
4. EXECUTE actions last (after all data prepared)

### Error Handling

- Check FAILED response for each entity type
- Process REPORTED messages by severity
- Use MAPPED to correlate %CID with actual keys
- Abort transaction if critical operations fail

## Common Patterns

### Create Parent-Child Hierarchy

```json
[
  {"op": "CREATE", "entity": "Parent", "instances": [{"%CID": "p1", ...}]},
  {"op": "CREATE_BY", "entity": "Parent", "sub_name": "_Child", "%CID_REF": "p1", "instances": [{...}]}
]
```

### Create and Update in Same Request

```json
[
  {"op": "CREATE", "entity": "Order", "instances": [{"%CID": "o1", ...}]},
  {"op": "UPDATE", "entity": "Order", "instances": [{"%CID_REF": "o1", "Status": "Confirmed"}]}
]
```

### Create and Execute Action

```json
[
  {"op": "CREATE", "entity": "Order", "instances": [{"%CID": "o1", ...}]},
  {"op": "EXECUTE", "entity": "Order", "sub_name": "Approve", "instances": [{"%CID_REF": "o1"}]}
]
```

### Multi-Level Hierarchy (3+ Levels)

```json
[
  {"op": "CREATE", "entity": "Route", "instances": [{"%CID": "r1", ...}]},
  {"op": "CREATE_BY", "entity": "Route", "sub_name": "_Visit", "%CID_REF": "r1", "instances": [{"%CID": "v1", ...}]},
  {"op": "CREATE_BY", "entity": "Visit", "sub_name": "_Delivery", "%CID_REF": "v1", "instances": [{"%CID": "d1", ...}]},
  {"op": "CREATE_BY", "entity": "Delivery", "sub_name": "_Item", "%CID_REF": "d1", "instances": [{...}]}
]
```
